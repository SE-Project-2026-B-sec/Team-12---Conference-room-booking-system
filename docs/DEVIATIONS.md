# Deviations from the SRS / SAD / Test Plan

Add one line per deviation: date, story key, what differs, why.

- 2026-10-28, CRBS-11: The three .docx documents are still at the repository root, not in `docs/` as the README says. Left in place so existing README links keep working; move them in a separate change.
- 2026-11-02, CRBS-31: The `findBookingConflict` pre-check used by CRBS-18 (outside the transaction, not race-safe) is replaced in `booking-service.ts` by a check inside one transaction that first locks the room row (`SELECT ... FOR UPDATE`) and then queries overlaps on the transaction client. `booking-conflict.ts` and `booking-overlap.ts` are unchanged and no longer called by the create-booking path.
- 2026-11-02, CRBS-31: A DB-level exclusion constraint (btree_gist) on overlapping CONFIRMED bookings was considered and deliberately not added, because of the migration risk to team databases and CI; the room row lock plus the in-transaction overlap check satisfies FR14/NFR02.
- 2026-11-02, CRBS-12: SRS says Docker Compose runs the demo application and PostgreSQL -> `docker-compose.yml` has one `app` service built from one multi-stage `Dockerfile` that serves both the API and the built client (static files from `public/`), plus a `db` service (postgres:16-alpine), both with healthchecks -> keeps the demo to one app container and one origin (no separate client container or CORS).
- 2026-11-02, CRBS-18: Nothing in the documents says the database port is published -> the compose `db` service publishes 5432 on `127.0.0.1` only -> tests that run on the host (`npm test`) need to reach PostgreSQL; loopback keeps it off the network.
- 2026-11-02, CRBS-18: SAD 4.3 and TC04 say POST /api/bookings returns `201: { bookingId, status }`; 400 is "invalid input" -> 201 also returns `roomId`, `startAt`, `endAt` (UTC ISO); 400 returns `{ error: { code, message }, fields: { <field>: <message> } }`; `userId` and `status` in the request body are ignored (userId comes from the session, status is always CONFIRMED) -> lets the frontend show the booking and per-field messages without a second call.
- 2026-11-02, CRBS-18: Test Plan says CI uses an isolated PostgreSQL service; it does not describe local database tests -> DB-backed tests use a separate `crbs_test` database named by `DATABASE_URL_TEST`; `tests/helpers/test-db.ts` and `scripts/prepare-test-db.mjs` refuse to run unless the database name ends in `_test`; one-time setup is in the README -> they can never touch the dev database.
- 2026-11-02, CRBS-18: Authentication stores bcrypt hashes at cost 12 (seed and `auth.test.ts`) -> the DB-backed tests I added hash their synthetic users' passwords at cost 4 -> only inside tests, to keep the suite fast; production hashing is unchanged.
- 2026-11-02, CRBS-24: Team process assumed GitHub branch protection on `main` (1 review, checks Server and Client) -> not enabled; Harish's repo role is Write, not Admin (`gh repo view` reported `WRITE`); stand-in is `.github/pull_request_template.md`, `.github/CODEOWNERS` (`* @harish-rameshkumar`) and README rules; Harish says the real protection is tracked as CRBS-47 (to confirm: the card is not referenced anywhere in the repo) -> protection needs repo admin.
- 2026-11-02, CRBS-28: SRS FR12 says "valid required fields" and "positive integer capacity" without limits -> admin room create/update enforce: `name` 1-100 characters (matches `VarChar(100)`), `location` 1-200 (matches `VarChar(200)`), `capacity` whole number 1-10000, `facilities` at most 50 entries of 1-100 characters each (trimmed, default `[]`), unknown fields ignored -> the upper limits for capacity and facilities are our choice, not from the SRS.
- 2026-11-02, CRBS-28: SAD 4.3 lists POST /api/admin/rooms with `201 / 400 / 403` only -> it also returns 401 (no session) and 403 for a missing or wrong CSRF token; PATCH /api/admin/rooms/:id (FR13) returns 200, 400 (invalid fields, empty body, or `:id` not a positive integer, with a `fields` map), 401, 403 and 404 (unknown room); all in the `{ error: { code, message } }` shape -> consistent with FR15 and the existing routes. SAD 4.3 has no PATCH row yet.
- 2026-11-02, CRBS-28: Test Plan does not mention test-file ordering -> `server/vitest.config.ts` sets `fileParallelism: false` -> DB-backed test files share one `crbs_test` database and some assert on whole-table listings (e.g. GET /api/rooms), which raced when files ran concurrently.
- 2026-11-02, CRBS-11: Jira cards are not linked to GitHub -> PR links are added to the Jira cards by hand (comment on each card), as the PR template checklist says -> (to confirm: this is a Jira setup fact that cannot be checked from the repository).
- 2026-11-02, CRBS-11: README says the sprint dates follow the announcement rather than the older image timeline -> the same dates are used here; (to confirm: the teacher's sheet dates were not available to check; if they differ the README Sprint schedule needs updating).
- 2026-11-06, CRBS-37: Test Plan calls for a deployment job on a self-hosted runner on a team laptop -> `cd.yml` has the `deploy` job (`runs-on: self-hosted`) gated behind the repo variable `DEPLOY_ENABLED == 'true'`, so it is skipped by default; a documented local script `scripts/deploy-local.sh` (builds or pulls the commit-tagged image, starts it with `docker-compose.deploy.yml`, runs `scripts/smoke-test.sh`) is the fallback -> we have no repo admin rights to register a runner. The image is published to ghcr.io tagged with the full commit SHA (and `latest`).
- 2026-11-06, CRBS-37: The Dockerfile built the server without generating the Prisma client -> `Dockerfile` now installs OpenSSL, runs `npx prisma generate` before `npm run build`, and copies the generated client into the runtime stage -> the image build failed on `main` (TypeScript could not find `BookingStatus`); CI did not catch it because CI runs `prisma generate` itself.
